## 一、总体结论（第三轮）

**评分：9.2 / 10**

这一轮的修复方式比修复数量更值得看：**`downloader.py` 从 895 行降到 818 行，同时新增了 416 分流、永久/暂时错误分流、进度口径统一三项能力。** 多数项目的"修完一堆 bug"意味着引擎越修越肿；这里是净减少，因为两个新模块把职责剥了出去：

| 新模块 | 行数 | 职责 |
|---|---|---|
| `src/httpinfo.py` | 128 | HTTP 语义判定与探测：`urllib` 把 4xx 抛成异常、拿不到 `r.status` 这件事收敛到一处 |
| `src/naming.py` | 77 | 文件名规整：纯函数、无副作用、不碰网络与磁盘 |

`httpinfo` 还顺带把「416 等于不支持分段」「401/403/404 是永久错误」「408/429 才值得退避」这套 HTTP 语义集中表达，`downloader` 只调用不看细节。这是分层该有的样子。

配套的 `docs/DESIGN-fix2.md`（1,724 行）不是方案说明书，是**带修订记录、风险清单、判定式汇总和任务分解**的施工图，其中一条方法论写得很准：

> 契约类规则的判据必须能被一段脚本复现。

这句话本身就是这个项目最值钱的东西——它把"文档说做到了"变成"脚本能验证做到了"。

## 二、独立验证（不采信报告自述）

所有"已修"均经我自行构造场景实跑，不复用仓库测试。

### 2.1 BUG-42 · 416 未识别（上轮我报告的 P2）

**六种组合矩阵**（HEAD 是否声称 `Accept-Ranges` × GET 实际行为）：

| HEAD 声称 | GET 行为 | `probe().ranges` | 下载结果 |
|---|---|---|---|
| 是 | 正常 206 | True | 成功 |
| 是 | 忽略 Range 回 200 | True | 成功（CORE-011 兜底） |
| 是 | **416 拒绝** | **False** | **成功** ← 上轮此处彻底失败 |
| 否 | 正常 206 | True | 成功（探针发现实际支持） |
| 否 | 忽略 Range | False | 成功 |
| 否 | 416 | False | 成功 |

修复方式正确：`probe()` 在 HEAD 声称支持后**无条件再做一次 `Range: bytes=0-0` 确认**，收到 416 即判 `ranges=False`；`_worker` 侧同步识别 `HTTPError.code == 416` 并计入 `_no_range_mirrors`，全部源都 416 时经 `_fatal` 走与 ENOSPC 相同的退化通路。

### 2.2 BUG-38 · 剪贴板空窗（上轮我翻案的那条）

用 `ast` 抽取 `gui.pyw` 真实方法体编译执行，复刻 `_watch_clip` 判定：

| 阶段 | 文本 | 视为空 | 已接管 | 剪贴板会填入 |
|---|---|---|---|---|
| 初始（占位符） | `https://…` | True | False | True |
| **点进输入框后** | 空 | True | **True** | **False** ← 空窗已封堵 |
| 聚焦后空手离开 | `https://…` | True | False | True ← 交还控制权 |

两个方向都对：聚焦即接管、空手离开即交还。不是简单地把剪贴板功能关掉。

### 2.3 BUG-31 · 校验器五类盲区

新增 8 项检查，我逐项注入违规验证**是否真能报红**（复制项目到临时目录改源码跑校验器）：

| 注入的违规 | 结果 |
|---|---|
| 在 `dl.py` 里访问 `DownloadTask._cancel` | 报红：`dl.py:281 访问了 downloader._cancel` |
| 删掉 `run()` 里的 `expand_mirror_urls` 调用 | 报红：`DownloadTask.run：没有调用 expand_mirror_urls` |
| 把 `SLOW_BYTES` 换成硬编码字面量 | 报红：`SLOW_BYTES 从未被读取` |
| 改 `SCHEMA` 内容但不升 `version` | 报红：指纹不符，报错自带 payload 键集诊断 |

四项全部有效。实现还有精度层面的自觉：`const_used` 的 `aliases` 故意留空，理由是「低精度规则吞掉高精度规则的判定是净负收益」；`call_site` 拒绝末段名近似匹配。这类取舍说明检查不是为凑数写的。

### 2.4 BUG-32 / 33 · 进度口径

真实 12 MB 六线程下载，全程采样 `progress`：`total` 恒定、`done` 单调不减、无一次越界、终值精确等于文件大小。契约 CORE-025 给出的判据式（`done = Σ _credited(size_i, want_i) ≤ total`）与实现一致，且**计入与扣减走同一函数**，口径不会分叉。

第二轮我提过「无 tkinter 环境整类 skip，导致 REQ-011/014/023 零验证」。本轮核实：

## 三、剩余可改进项（1 条，P3，非缺陷）

**`probe()` 的确认探测只处理 416，未处理「HEAD 声称支持、GET 返回 200 且无 Content-Range」。**

实测这一组合 `ranges` 仍为 `True`，于是先走分片路径、每个分片收到 200、全部记入 `_no_range_mirrors`、再退化单线程重下。**结果正确**（CORE-011 兜底），只是多绕一圈，大文件上会浪费分片阶段的请求与部分传输。

既然确认请求已经发出去了，顺手判掉是零成本：响应 200 且无 `Content-Range` 即 `ranges = False`。当前不列为缺陷——`probe()` 的 docstring 明确只针对 416（BUG-42 的范围），且 200 场景有既有机制兜底，属设计权衡。

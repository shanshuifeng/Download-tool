## 热更新机制

文档不是一次性产物，靠三层保证它不腐烂：

**第一层｜机器可读契约块**
每份 `CONTRACT-*.md` 里带若干 ```contract 围栏块（JSON）。它既是给人看的规格，也是校验器的输入。改接口时**先改这里**，再改代码。

**第二层｜可执行校验**
```bash
python docs/verify_contract.py
```
逐条比对文档声明与代码现状，发现漂移即失败（退出码 1）。加 `--verbose` 打印每条检查的细节。

**第三层｜代码锚点**
关键实现点用注释锚定契约编号：

```python
self.threads = max(1, min(int(threads), 64))   # @contract CORE-004
```

校验器会双向检查：代码里引用了不存在的契约编号 → 报错；某条契约在代码里找不到锚点 → 提示（不阻断）。

## 变更协议

1. 任何**接口形状**的变化（函数签名、参数、事件字段、文件格式、退出码）必须先改契约文档
2. 改完跑 `verify_contract.py`，确认从「预期失败」变成「通过」
3. 同步更新 `REQ.md` 里对应条目的状态
4. 在下方变更记录追加一行
5. 纯内部重构（不改接口形状）不需要动契约，但若锚点编号变了要同步

## 兼容性红线

- `dl.exe --json` 的事件字段、退出码：**只增不改**。已发布给 Agent 用的接口不能回归
- `config.json` 的既有键：只增不改语义；新键必须有默认值，缺省时行为等同旧版
- `DownloadTask` 的既有参数：只增不改，新参数一律带默认值
- `meta.json` 的既有字段：只增不改；新增字段缺失时按旧逻辑回退

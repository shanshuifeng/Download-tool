# 契约文档索引

本目录是本项目实现层面的唯一事实来源。仓库根目录的 `README.md` 面向使用者，本目录面向参与维护的人。

## 阅读路径

| 目的 | 建议顺序 |
|---|---|
| 了解如何使用 | 根目录 `README.md`（快速开始 → 界面 → 自动化接口）；`使用说明.txt` 为一页纸版本 |
| 了解需求来源 | `REQ.md`：需求拆分、验收标准、状态与需求↔测试对照表 |
| 了解接口约束 | `CONTRACT-engine.md`、`CONTRACT-cli.md`、`CONTRACT-gui.md`、`CONTRACT-data.md`、`CONTRACT-code.md` |
| 了解已知问题 | `BUGS.md`：42 条缺陷的成因、处置方式与验证方式 |
| 了解代码组织 | `src/downloader.py` 为引擎（探测、分片、校验）；`src/dl.py` 为唯一命令行接口；`src/taskqueue.py` 为多任务调度；`src/gui.pyw` 为界面兼唯一入口；`src/netio.py` 为传输层；`src/httpinfo.py` 为 HTTP 语义判定与探测；`src/naming.py` 为文件名规整；`src/mirrors.py` 为加速源策略；`src/diskutil.py` 与 `src/resume.py` 分别负责落盘预检与续传指纹 |
| 提交改动 | 顺序固定：先写测试，再改契约，最后改代码；收尾执行 `python docs/verify_contract.py` 与 `python -m unittest discover -s tests` |

## 基本约束

以下三条由 `CONTRACT-code.md` 展开定义，并由校验器强制：

1. **仅使用标准库。** 引入第三方依赖会破坏单文件、可移动的交付形态。
2. **接口形状变更先改契约文档。** 校验器以文档为准；只改代码不改文档会导致校验失败。
3. **每条标记完成的需求都需要对应的测试**，且测试体内必须写明需求编号，校验器双向核对。缺陷报告中的条目同样受此约束。

## 文档与代码的一致性保障

文档与实现之间通过三层机制保持同步。

**第一层：机器可读的契约块。** 每份 `CONTRACT-*.md` 中包含若干 ```contract 围栏块（JSON）。这些块既是规格说明，也是校验器的输入。接口变更应先修改此处。

**第二层：可执行校验。**

```bash
python docs/verify_contract.py
```

校验器逐条比对文档声明与代码现状，发现漂移即以退出码 1 结束。`--verbose` 输出每项检查的细节，`--json` 输出机器可读结果。当前共 25 项检查。

**第三层：代码锚点。** 关键实现点通过注释绑定契约编号：

```python
self.threads = max(1, min(int(threads), 64))   # @contract CORE-004
```

校验器只做单向检查：代码引用了文档中不存在的契约编号即报错。反向检查（契约编号未在代码中设置锚点）不纳入校验——部分条目属于文档级约定，强制要求锚点只会产生无意义的标注。

## 变更协议

1. 涉及接口形状的变更（函数签名、参数、事件字段、文件格式、退出码），必须先修改契约文档
2. 修改后执行校验器，确认结果由预期失败转为通过
3. 同步更新 `REQ.md` 中对应条目的状态
4. 在下方变更记录中追加一行
5. 纯内部重构不涉及契约文档；若锚点编号发生变化则需同步

## 兼容性约束

以下内容对已发布的调用方构成契约，只能新增，不能改变语义：

- `下载工具.exe --json` 的事件字段与退出码
- `config.json` 的既有键。新增键必须带默认值，缺省时行为与旧版本一致
- `DownloadTask` 的既有参数。新增参数只能追加在末尾并带默认值
- `meta.json` 的既有字段。新增字段缺失时按旧逻辑回退

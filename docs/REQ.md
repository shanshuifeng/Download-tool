# 需求拆分

共 25 条需求：24 条已完成，REQ-008b 经评估不做。

## 拆分原则

1. **每条需求必须可独立验收** —— 有自己的通过条件，不依赖别的需求先完成
2. **一条需求只改一个契约面** —— 要么改引擎、要么改 CLI、要么改数据格式，混在一起就拆
3. **优先级只按「会不会出错」和「能不能测出差异」定** —— 不按工作量
4. **明确不做的范围** —— 划定边界，避免功能无节制扩张

## 明确不做

| ID | 项 | 理由 |
|---|---|---|
| X-01 | BT / 磁力 / eD2k | 需要 libtorrent，破坏零依赖；且与「直链工具」定位冲突 |
| X-02 | HLS / DASH / yt-dlp 集成 | 属于内容解析层，不在本工具职责范围内；纳入后引擎复杂度显著上升 |
| X-03 | TLS 指纹伪装 | 规避风控的合规风险，与定位无关 |
| X-04 | 浏览器扩展 | 商店审核 + 全站权限信任，成本远高于剪贴板方案（REQ-011） |
| X-05 | HTTP/2 / QUIC | 标准库不支持，引入即破功 |
| X-06 | 自动更新 | 自签名证书做更新没有安全意义 |
| X-07 | 多语言 | 单人工具，收益为零 |

## 状态跟踪

改完一条需求：先在 `tests/` 写用例并在 docstring 里声明 `REQ-编号`，再把编号挂到上表，
最后把状态改为 `已完成`。顺序不可颠倒——先标状态后补测试，会产生「标记完成但实际不可用」
的结果。
